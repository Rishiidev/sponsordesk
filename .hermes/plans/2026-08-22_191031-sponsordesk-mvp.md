# SponsorDesk MVP Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to execute this plan task-by-task. Two-stage review (spec compliance then code quality) per task.

**Goal:** Ship a working web + PWA app at `app.sponsordesk.io` where individual creators can manage brand-deal pipelines, get auto-reminders, track deliverables, and store brand contact history — with a free tier (3 active deals) and a $9/mo Pro tier.

**Architecture:** Single Next.js 15 app on Vercel, with Supabase (Postgres + Auth + Storage + RLS) as the data layer. Marketing site stays on its current Vercel deployment (`sponsordesk-waitlist.vercel.app`) until the new domain DNS is live. PWA features (service worker, push, offline) are part of the same Next.js codebase.

**Tech Stack:**
- **App:** Next.js 15 App Router + Tailwind v4 + Motion
- **Data:** Supabase (Postgres + Auth + Storage + RLS)
- **Auth:** Supabase Auth (email + Google + magic link)
- **Email:** Resend
- **Payments:** Stripe Checkout + Customer Portal
- **Cron:** Vercel Cron
- **Analytics:** PostHog
- **PWA:** Service worker (next-pwa or Serwist), Web Push API
- **Deployment:** Vercel (single app, two routes: marketing + app)

**Code sketch for `server.ts`:**
```typescript
import { createServerClient } from '@supabase/ssr';
import { cookies } from 'next/headers';

export async function createClient() {
  const cookieStore = await cookies();
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll: () => cookieStore.getAll(),
        setAll: (toSet) => {
          try { toSet.forEach(({ name, value, options }) => cookieStore.set(name, value, options)); }
          catch {}
        },
      },
    }
  );
}
```

### Task 1.3: Run initial Supabase migration

**Files:**
- Create: `supabase/migrations/0001_init.sql`

**Steps:**
1. Use the Supabase SQL editor (or `supabase` CLI) to create the migration
2. Define the `users` table (Supabase Auth handles this — but we need a `public.profiles` table for app-specific data)
3. Add RLS policies: users can only see their own profile

**SQL:**
```sql
-- Public profile table linked to auth.users
create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  email text not null,
  full_name text,
  creator_handle text,        -- @channelname for creator context
  follower_count text,         -- "10K-50K" etc
  deal_volume text,            -- "1-3 / month" etc
  timezone text default 'UTC',
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

-- RLS
alter table public.profiles enable row level security;

create policy "Users can view own profile"
  on public.profiles for select
  using (auth.uid() = id);

create policy "Users can update own profile"
  on public.profiles for update
  using (auth.uid() = id);

-- Auto-create profile on signup
create or replace function public.handle_new_user()
returns trigger as $$
begin
  insert into public.profiles (id, email)
  values (new.id, new.email);
  return new;
end;
$$ language plpgsql security definer;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

**Verification:** Run `\dt public.*` in Supabase SQL editor — should see `profiles` table. Sign up a test user in Supabase Auth dashboard — should auto-create a profile.

| Single founder burnout | Ship in 6-8 weeks, take 2-week break, ship phase 2. |
